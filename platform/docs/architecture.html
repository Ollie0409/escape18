Escape 18 platform: architecture and hosting costs

Status: prototype, nothing deployed. Limits below were checked on the official pages on 19 Nov 2026. Free tiers change, so re-check before going live.

1. Summary and components

The platform is one static web app (teacher dashboard, pupil shell, landing page) that runs the existing Escape 18 lessons unchanged inside a same-origin iframe. A small bridge script (lessons/config.js) catches the events the lesson engine already sends and passes them to the pupil shell with postMessage. The shell sends them to a realtime class relay (a Cloudflare Worker plus one SQLite-backed Durable Object per class, EU jurisdiction, WebSocket Hibernation), which feeds the teacher's live view. Research logging to the existing Google Sheet stays optional and off by default. A service worker caches the app so pupils can still play, and get a result code, when the relay is unreachable. No accounts, names, cookies or free text.

4. Capacity estimate

Assumptions: 1 class = 15 pairs (15 pupil devices) + 1 teacher = 16 sockets. ~40 pupil frames per pair per lesson (batch about every 15 s plus room ends). ~1 teacher update per pupil frame. Each socket reconnects twice on average (flaky school wifi). Batches of 15 s are what the SPEC allows; relay coalesces teacher updates to max 2/s.

Per class

  • Incoming pupil frames: 15 x 40 = 600. Add 15 hello frames, ~15 timer/state frames from the teacher, ~20 pings: about 650 incoming.
  • DO requests: 650 / 20 = 33 (message billing) + 16 connections + 30 reconnects = about 80.
  • Worker requests: 1 create-class POST + 16 upgrades + 30 reconnects = about 47, call it 50.
  • Outgoing frames (acks 600 + teacher updates 600 + timer broadcasts): about 1,300, free.
  • SQLite rows written: one upsert per pupil frame = 600, plus class and team rows ~50: about 650. Rows read: small (well under 5 M).
  • Duration: with hibernation, active time is short bursts. Assume 50 ms per frame: 650 x 0.05 s x 0.128 GB = about 4 GB-s (estimate). Without hibernation, a 45 min lesson holds the object in memory: 2,700 s x 0.128 GB = about 346 GB-s per class.

Per school day, 50 classes

Resource Use Free limit Headroom Max classes/day at limit
Worker requests 2,500 100,000 40x ~2,000
DO requests 4,000 100,000 25x ~1,250
DO rows written (naive upsert per frame) 32,500 100,000 3x ~150
DO duration with hibernation ~200 GB-s 13,000 65x ~3,000
DO duration without hibernation ~17,300 GB-s 13,000 none ~37

Findings: the binding limit is rows written, not requests. Fix is cheap: keep TeamState in memory and write to SQLite only on room change, join, end and every 30 s (about 10 to 15 writes per team, ~200 rows per class), giving ~500 classes/day. Hibernation is mandatory, not an optimisation. Whether index writes count as extra rows is unverified; leave 2x margin.

Research log (only when ticked): ~30 events per pair per lesson, batched about every 15 s, so about 1 POST/s per class and 1 to 2 concurrent executions per class. The 30-simultaneous limit allows roughly 15 research classes at the same moment. Fine for a pilot.

A pilot (5 schools, 10 classes on a busy day) uses about 1% of the free limits.
